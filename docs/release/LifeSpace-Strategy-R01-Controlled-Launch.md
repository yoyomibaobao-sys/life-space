# LifeSpace｜受控正式上线执行计划 R01

**决策日期：2026-11-16**

**目标：停止大规模 QA，合并统一版本，正式投入受控真实使用，以实际使用反馈驱动后续迭代。**

## 1. 项目管理规则

1. 不再要求原 160 项全部 PASS 才能上线。
2. 已有 PASS 证据继承，不重复安排大规模测试矩阵。
3. QA 环境保留为历史验证环境，不再作为普通代码修改的必经环节。
4. 所有代码修改进入统一源码分支和版本管理。
5. 真实使用发现问题后，按 P0/P1/P2 分级修复，构建可追溯的小版本。
6. 数据库、身份权限、数据删除、支付、媒体存储迁移仍保留最小安全门禁。
7. 生产 SQL、正式 Worker、域名切换、R2 开关及 APK 分发分别执行授权。

## 2. 第一阶段：统一源码与发布版本

责任任务：137、142。

- 以 W4 回退候选 90a9c8b 和 142 R02 候选 4e00ff41 为基础。
- 保留原统一 checkout 的 6d85989、49 项未提交现场和原始交付文件。
- 在独立 managed worktree 中完成源码合并，不覆盖原工作树。
- 核对 W4、W5、媒体 Worker 配置差异，冻结唯一正式 Release Commit。
- W4、W5、R2 媒体和 PayPal 使用同一发布基线构建，记录各产物 SHA-256；业务代码与正式运行开关分开管理。
- 不把本地候选提交、源码合并或构建结果误称为正式部署。

## 3. 第二阶段：正式数据库准备与安装

责任任务：023、040、144、145。

冻结安装顺序：

1. R39 R02
2. 020 R02
3. 正式适配 R10 R01
4. 040 安装包装
5. 144 R04

要求：

- 保留五份冻结 SQL 原件及 SHA-256。
- 040 R16 Gate SQL 完成静态审查和安装链兼容性判断前，不加入正式安装链。
- 正式窗口核实 Cron、在途任务、写入口、主账号和 Owner。
- 使用维护窗口及必要停写保护；每一步确认事务提交和数据库后像后才继续。
- 安装后由 145 只读核对迁移、对象、字段、函数、策略和权限。
- 未知状态立即 STOP，不盲目重试。
- R39 提交后，不得回退到已知不兼容的旧 v93。

## 4. 第三阶段：网站受控上线

责任任务：142、148。

- 使用与新数据库合同兼容的正式 W4。
- 首期沿用已验证的 Supabase Storage 读取路径；R2 业务代码、独立 Worker 和正式 Service Binding／vars 配置随同一 Release Commit 与 W4/W5 构建保留。
- R2 读写开关首期可保持 false，直至正式媒体 Worker、桶、Binding、HMAC Secret、Rate Limiting binding 和回退入口就绪；这是运行时门禁，不是源码拆分。
- W4 正式构建必须包含正式媒体 Service Binding 接线；正式 Worker 未创建前不执行正式部署。
- 保留兼容版本和恢复路径，分阶段切换。
- 首期只开放受控真实使用范围，不自动开启搜索收录或公众推广。

## 5. 第四阶段：Android 正式发布

责任任务：137、139、150。

- 使用统一 Release Commit 构建正式 APK。
- 核对包名、正式 Supabase 地址、Worker 地址、签名证书及 versionCode。
- 已有 v29 签名和真机升级证据按原范围继承，但最终发布 APK 必须与本次统一版本一致。
- 先受控使用，再扩大分发范围。

## 6. 第五阶段：真实使用与迭代

责任任务：151–160。

重点观察：

1. 网页与 APP 登录、刷新和 Owner 归属。
2. 网页创建项目、种植记录及关联数据。
3. APP 读取和同步网页新增内容。
4. 图片上传、跨端显示及媒体归属。
5. Free／Plus 权益。
6. Guide 读取、管理员审核和投影。
7. 多账号 Owner 隔离。
8. 数据完整性和容量账本。

只做新环境必要的最小冒烟，不重复历史已通过的矩阵。

问题分级：

- **P0：**数据丢失、越权或严重安全问题，立即停止相关功能并恢复安全状态。
- **P1：**登录、记录、图片等核心功能故障，优先修复并发布小版本。
- **P2：**显示、交互和体验问题，进入常规迭代。

## 7. R2 与 PayPal：必须进入统一源码，运行时分阶段启用

**统一源码原则：R2 和 PayPal 均属于 LifeSpace 正式产品能力，必须保留在同一个 Release Commit、W4/W5 构建和发布分支中。不得因首期运行开关关闭而拆出源码、排除构建或另建长期分支。**

### R2 媒体

责任任务：112、120–128、133、141、142、147、149、157。

- 统一源码必须包含 R2 业务媒体 Worker、私有读取授权、镜像写入、SHA 完整性校验、Supabase Storage 回退和 W4 Service Binding 接线。
- 本轮源码已包含 R2 业务处理器和独立 Worker 入口；当前正式媒体资源尚未就绪，业务处理器仍有明确关闭保护。
- 继续把正式 Worker、私有桶、Service Binding、HMAC Secret、写入保护和可恢复回退纳入同一 Release Commit 的配置与部署产物；不得以“暂不启用”为由删除或漏构建。
- 正式资源和切换入口准备好后，R2 读写作为同一产品版本的受控功能启用；开关关闭仅表示尚未切换，不表示功能不合并。

### PayPal

责任任务：143。

- 统一源码必须包含订单创建、Capture、会员权益确认、Webhook 签名验证、幂等处理和支付状态对账代码，并随 W4/W5 同一 Release Commit 发布。
- 当前正式收费保持关闭；先补齐一次受控 Sandbox Capture、Webhook 重放幂等、订单与会员状态核对及人工退款流程确认。
- 这些是支付服务正式启用的最小资金安全门禁，不是要求恢复原 160 项 QA 矩阵，也不是把 PayPal 从统一源码中排除。
- 退款由管理员在 PayPal 商户后台人工处理，应用不自动发起退款。

## 8. 首期受控使用的最低门禁

- [ ] 唯一正式源码 Commit 冻结。
- [ ] W4、W5、R2、PayPal 均纳入同一 Release Commit 和发布产物。
- [ ] W4、W5 与正式数据库合同一致。
- [ ] R16 是否进入安装链已有明确结论。
- [ ] 正式 SQL 安装窗口前置条件通过。
- [ ] 数据库安装及 145 后像核对通过。
- [ ] W4 正式版本和兼容恢复版本就绪。
- [ ] Storage 回退路径可用；R2 正式资源就绪后按同一版本启用，不另拆源码。
- [ ] PayPal 正式收费在 Sandbox Capture／Webhook 幂等闭环前保持关闭。
- [ ] 正式 APK 与统一发布版本一致。
- [ ] 主账号、权限、Owner 和基本业务功能完成最小核验。
- [ ] 对应正式发布操作取得授权。

**最终原则：不再为了完成测试而推迟产品投入使用，也不为了赶上线而牺牲数据安全。**

**本计划不是正式公开收费发布批准；PayPal Live 收费、公众推广、搜索收录和 R2 正式读写仍按各自运行门禁启用，但 R2 与 PayPal 源码必须随统一版本一并合并和构建。**
